# ADR-003: Глобальное развёртывание GoFuture

**Статус:** ⚠️ На рассмотрении  
**Участники:** Глушенко Сергей  
**Дата:** 2026-04-26

---

## 1. Контекст

Платформа GoFuture находится в процессе перехода от монолита к микросервисной событийной архитектуре. Бизнес требует обработки до 500 тысяч конкурентных поездок, активной экспансии на рынки Юго-Восточной Азии и Южной Америки, а также обеспечения доступности 99.95% (цель 99.99% для критических компонентов) и низкой задержки для пользователей в этих регионах. Существующая инфраструктура на базе Яндекс.Облака не имеет точек присутствия в целевых регионах, что требует мультиоблачной (или гибридной) стратегии и глобального геораспределённого развёртывания.

## 2. Требования

- Обработка 500 тысяч конкурентных поездок в реальном времени, с глобальным покрытием.
- Развёртывание более чем в трёх географических регионах для близости к конечным пользователям.
- Обеспечение доступности критических сервисов на уровне 99.99%.
- Низкая задержка (p99 < 200 мс для API критического пути) для пользователей в Юго-Восточной Азии и Южной Америке.
- Соблюдение локальных регуляторных требований по резидентности данных.
- Автоматическое аварийное переключение между регионами при катастрофических сбоях.
- Защита от DDoS, атак на прикладном уровне, соответствие стандартам безопасности.

## 3. Решение

### 3.1 Обоснование выбора регионов

Для достижения низкой задержки и выполнения регуляторных требований выбраны следующие основные регионы:

| Регион                   | Провайдер / Зона                 | Обоснование                                                                                                                                                                                                 |
| ------------------------ | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Москва (Россия)**      | Yandex Cloud (ru-central1)       | Текущий основной регион, legacy-инфраструктура, центр разработки. Обеспечивает работу существующих клиентов и сервисов.                                                                                     |
| **Сингапур**             | AWS (ap-southeast-1)             | Оптимальная точка для Юго-Восточной Азии (Индонезия, Таиланд, Вьетнам, Филиппины). Низкая задержка до основных рынков, развитая сетевая инфраструктура, соответствие местным требованиям к хранению данных. |
| **Сан-Паулу (Бразилия)** | AWS (sa-east-1)                  | Крупнейший рынок Латинской Америки. Низкая задержка для Бразилии, Аргентины, Чили. Наличие местных ЦОД, возможность выполнения законов о локализации данных (LGPD).                                         |
| **Франкфурт (Германия)** | AWS (eu-central-1) (опционально) | Резервный европейский регион для обеспечения отказоустойчивости и обслуживания европейских партнёров.                                                                                                       |

Такой выбор покрывает все целевые географические зоны, минимизирует задержку для конечных пользователей и даёт возможность изолировать данные в соответствии с местным законодательством (residency).

### 3.2 Схема репликации данных между регионами

Применяется многоуровневый подход к репликации данных, основанный на их природе и требованиях к согласованности и задержке.

- **Глобальные данные (мастер-справочники):** профили клиентов (пассажиров, водителей), конфигурации тарифов, шаблоны уведомлений.  
  *Механизм:* асинхронная репликация через **Kafka Connect (CDC)** с топиками‑источниками в каждом регионе и **MirrorMaker 2** для кросс‑региональной доставки aggregator‑топика. Базы‑получатели обновляются через потребителей CDC.
- **Региональные данные:** поездки, финансовые транзакции, локации водителей.  
  *Механизм:* хранятся строго в пределах региона (data residency). Репликация не производится, за исключением обезличенных агрегатов для аналитики (через Kafka). Для катастрофоустойчивости критичные данные (активные поездки) могут реплицироваться в парный регион асинхронно с помощью **PostgreSQL Streaming Replication** или **Cassandra multi‑DC** (гео‑треки).
- **Событийная шина:** для каждого региона разворачивается **локальный кластер Kafka**. Глобальные события (профили, fraud‑сигналы) реплицируются между регионами через **MirrorMaker 2**, настроенный на избранные топики с префиксами `global.*`. Региональные события (например, `ride‑events`) остаются локальными.

Такая схема минимизирует межрегиональный трафик, уменьшает задержки и обеспечивает соблюдение требований резидентности.

### 3.3 Механизм геомаршрутизации пользователей

В основе геомаршрутизации лежит **DNS‑базированная маршрутизация** в сочетании с **Anycast** и **Health Checks**.

- Домен API: `api.gofuture.io` обслуживается глобальной DNS‑службой (Amazon Route 53 или Cloudflare DNS) с политикой геомаршрутизации (Geo DNS).
- Для каждого региона настраивается своя запись A/AAAA, указывающая на публичный IP балансировщика в данном регионе (AWS Global Accelerator или региональный ALB/NLB).
- DNS‑сервер, получая запрос, определяет страну/регион пользователя по IP рекурсивного резолвера и возвращает IP ближайшего региона.
- Все клиентские приложения используют единое доменное имя без хардкода региональных адресов.
- Дополнительно на уровне приложения может использоваться сетевая оптимизация: мобильное приложение при старте замеряет задержки до зарегистрированных эндпоинтов и выбирает регион с минимальным RTT (фолбек, если DNS‑геотаргетинг не точен).

В случае недоступности ближайшего региона (по данным Health Checks) DNS автоматически переключает трафик на следующий доступный регион (failover).

### 3.5 Стратегия соответствия локальным регуляторным требованиям

- **Data Residency:** все персональные данные пассажиров, водителей и данные о поездках хранятся исключительно в регионе, обслуживающем данную страну. Для Бразилии – только в Сан-Паулу, для Индонезии – в Сингапуре (при необходимости может быть добавлен локальный регион в Джакарте в будущем). Межрегиональный обмен осуществляется только обезличенными или агрегированными данными.
- **Шифрование:** данные в покое шифруются с помощью KMS каждого облачного провайдера, ключи управляются локально. Каналы связи между регионами защищены TLS 1.3 с взаимной аутентификацией.
- **Платежи и выплаты:** используются исключительно локальные платёжные шлюзы (банки, местные эквайринги), проходящие по PCI DSS. Данные карт не хранятся, токенизируются.
- **Аудит и отчётность:** для каждого региона настроен отдельный account/logging, журналы аудита не покидают регион. Внедрены политики IAM с разграничением доступа команд к данным разных регионов (принцип минимальных привилегий).
- **Регуляторные согласования:** архитектура позволяет развернуть новый изолированный регион при входе в новую страну за 2–4 недели, поскольку все сервисы упакованы в контейнеры и конфигурируются через GitOps.

### 3.6 Доработанная диаграмма C2 с защитными инструментами

Представленная диаграмма является расширенной версией целевой архитектуры из ADR‑001. Дополнительно внедрены следующие компоненты безопасности:

* **Защитный периметр (Security Perimeter)** — WAF и Anti‑DDoS на базе Cloudflare/AWS Shield, размещённые перед единым API Gateway. Весь внешний трафик пользователей проходит через этот эшелон.
* **Централизованный Identity & Access Management** — Keycloak как единый поставщик токенов (OAuth2/OIDC). API Gateway и Partner Gateway делегируют ему аутентификацию и авторизацию.
* **Service Mesh (Istio)** — инфраструктурный компонент, обеспечивающий автоматический mTLS для всех синхронных вызовов между сервисами, а также сетевые политики и трассировку.
* **Механизмы сетевой безопасности** (не отображаются на C2‑уровне, но подразумеваются): Kubernetes Network Policies и Cloud Security Groups, ограничивающие допустимые источники трафика до минимума.

```plantuml
Rel_L(payout_svc, bank_api, "инициирование выплат")
Rel(partner_gateway, matching_svc, "партнёрский доступ")
Rel(partner_gateway, pricing_svc, "партнёрский доступ")

' Связь с Service Mesh (инфраструктурная)
' Все синхронные вызовы автоматически проходят через sidecar-прокси Istio
@enduml
```

Пояснения к схеме:

- **Security Perimeter** — первый рубеж обороны. WAF анализирует входящие запросы, блокирует OWASP Top 10 атаки, а Anti‑DDoS защищает от volumetric атак. После фильтрации трафик направляется в API Gateway.
- **IAM (Keycloak)** — единый сервер авторизации. API Gateway и Partner Gateway проверяют предъявленные JWT‑токены через интроспекцию, не храня учётные данные пользователей локально.
- **Service Mesh (Istio)** — внедрён в кластер Kubernetes. Все поды содержат sidecar‑прокси Envoy, через которые прозрачно проходят синхронные вызовы. Istio обеспечивает автоматический взаимный TLS, централизованное управление политиками доступа (AuthorizationPolicy) и телеметрию. Связи на диаграмме помечены `gRPC (mTLS)` для явного указания защиты.
- **Сетевые политики** уровня инфраструктуры (Kubernetes NetworkPolicy, Security Groups) не изображаются на C2‑уровне, но гарантируют, что, например, Payment Service может инициировать исходящие соединения только к платёжным шлюзам, а не к произвольным узлам.

## 4. Альтернативы

- **Использование одного глобального кластера Kafka с расстановкой брокеров по регионам:** высокие задержки записи, проблемы с порядком сообщений, невозможность изоляции региональных данных. Отвергнуто.
- **Полная синхронная репликация между регионами:** слишком большая задержка для write-операций, противоречит требованию <200 мс. Для активных поездок это неприемлемо.
- **Отказ от мультиоблачности и использование только Yandex Cloud с новыми зонами:** Yandex Cloud на момент планирования не имеет ЦОД в ЮВА и Южной Америке, поэтому не удовлетворяет бизнес-требованиям.
- **Децентрализованная федерация идентификации:** усложнила бы аудит и потребовала бы синхронизации учёток, что увеличивает риск нарушения безопасности. Централизованный Keycloak оправдан.

## 5. Компромиссы

- **Eventual Consistency для глобальных данных:** полная согласованность недостижима без значительного роста задержек. Бизнес-логика должна быть спроектирована с учётом возможных расхождений.
- **Ручная активация резервного региона для некоторых служб:** не все сервисы могут быть переведены полностью автоматически без риска потери данных (требуется проверка консистентности БД).
- **Дополнительные затраты на инфраструктуру:** мультирегиональное развёртывание удорожает обслуживание, но окупается за счёт повышения доступности и снижения задержек.
- **Сложность управления мультиоблачной средой:** требуется унифицированный toolchain (Terraform, Kubernetes, Prometheus) для снижения операционной нагрузки.
