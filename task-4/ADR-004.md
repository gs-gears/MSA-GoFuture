# ADR-004: Проектирование аналитической платформы для ML и BI

**Статус:** ⚠️ На рассмотрении

**Участники:** Глушенко Сергей

**Дата:** 2026-04-26

---

## 1. Контекст

Бизнес-стратегия GoFuture требует data‑driven решений: динамическое ценообразование в реальном времени, прогнозирование спроса, обнаружение мошенничества и предоставление отчётности корпоративным клиентам, бухгалтерии и менеджменту.  
Ранее (ADR‑001, ADR‑002) принята целевая микросервисная архитектура с центральной событийной шиной Apache Kafka и CDC из баз данных. Это создаёт основу для единого пайплайна сбора, обработки и анализа данных.  
Настоящий ADR описывает, как именно данные из всех микросервисов собираются, обрабатываются и предоставляются ML‑моделям и BI‑инструментам, а также определяет механизмы обеспечения качества данных на всём пути.

## 2. Требования

- **Единая платформа сбора** данных из всех микросервисов без создания нагрузки на мастер‑базы.
- **Потоковая и пакетная обработка** для real‑time аналитики (ML‑фичи) и глубокого анализа исторических данных.
- **Интеграция с ML‑инструментами** для тренировки, регистрации и обслуживания моделей (Model Serving).
- **BI‑отчётность** для продуктовых менеджеров, финансистов и региональных руководителей.
- **Качество данных:** полнота, точность, своевременность, отсутствие дубликатов, прозрачность происхождения (data lineage).
- **Масштабируемость** до объёмов петабайт и конкуренции 500k активных поездок.

## 3. Решение

### 3.1 Lambda/Kappa‑гибридная архитектура аналитической платформы

Платформа разделяется на четыре логических слоя, центральной частью (нервной системой) остаётся кластер **Apache Kafka**.

**Уровень сбора (Ingestion Layer)**

- Все транзакционные данные из микросервисов поступают в Kafka через механизм **CDC (Debezium) + Transactional Outbox**, зафиксированный в ADR‑001. Это не создаёт дополнительной нагрузки на мастер‑базы.
- Высокоинтенсивные потоки (координаты водителей, сырые события геопозиции) публикуются напрямую в Kafka из сервисов без посредников.

**Уровень хранения (Storage Layer – Data Lake & DWH)**

- **Data Lake (сырое хранилище):** *Kafka Connect S3 Sink* непрерывно копирует топики в объектное хранилище (S3 / MinIO) в формате **Apache Parquet** со сжатием. Здесь хранится полная немодифицированная история – «песочница» для data‑сайентистов и аудита.
- **Data Warehouse (DWH):** витрины данных, оптимизированные для аналитических запросов, размещаются в колоночной СУБД **ClickHouse**. Она способна обслуживать интерактивные BI‑дашборды.

**Уровень обработки и ML (Compute & ML Layer)**

- **Real‑Time ML (Streaming Analytics):** **Apache Flink** непрерывно читает Kafka, агрегирует online‑фичи (например, «плотность водителей в квадрате 2×2 км за последние 5 минут»), передаёт их в Model Serving API и публикует результаты (Surge Multiplier) обратно в Kafka.
- **Batch Processing & ETL:** **Apache Spark** читает Parquet‑файлы из Data Lake, выполняет очистку, нормализацию и обогащение, после чего загружает подготовленные витрины в ClickHouse. Этот же кластер используется для подготовки и валидации обучающих датасетов.
- **ML Platform (Тренировка и регистрация моделей):** Data-scientists работают в **JupyterHub / AWS SageMaker**, подключаясь к Data Lake. Обученные модели сохраняются в **MLflow Model Registry**. Прошедшие проверку модели развёртываются в **Model Serving** (Seldon Core / KFServing), который предоставляет gRPC/REST API для синхронного инференса.
- Транзакционные сервисы (Fraud Detection, Pricing) вызывают модели синхронно через gRPC в момент обработки заказа.

**Уровень визуализации (BI Layer)**

- Для бизнес‑пользователей развёрнут **Apache Superset** (альтернативно Redash). Он подключается напрямую к ClickHouse и формирует дашборды: выручка, отказы, время ожидания, поездки по регионам.

### 3.2 Обеспечение качества данных

Качество данных гарантируется комбинацией организационных и технических мер на каждом этапе пайплайна.

| Уровень         | Механизм                          | Описание                                                                                                                                                                          |
| --------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Ingestion**   | Валидация схем (Schema Registry)  | Все продюсеры регистрируют Avro‑схемы. Брокер не пропускает событие с несовместимой структурой (Confluent Server‑side validation).                                                |
| **Ingestion**   | Идемпотентность записей           | Каждое событие содержит уникальный `eventId`. Консьюмеры и CDC‑приёмники проверяют уникальность перед записью в озеро/витрину.                                                    |
| **CDC**         | Мониторинг лага                   | Debezium‑лаг и отставание репликации (PostgreSQL LSN) контролируются алертами. При превышении порога инженеры уведомляются.                                                       |
| **Storage**     | Периодический аудит Parquet       | Фоновые Spark‑джобы проверяют целостность файлов, наличие всех ожидаемых партиций и соответствие схем.                                                                            |
| **ETL (Spark)** | Дедубликация и очистка            | Батч‑обработка удаляет дубликаты по бизнес‑ключу, приводит координаты к единому формату, отбрасывает записи с невозможными значениями (например, отрицательная стоимость).        |
| **ETL (Spark)** | Валидация бизнес‑правил           | Проверяются инварианты: сумма платежа > 0, время завершения поездки позже начала, водитель не может быть назначен на две поездки одновременно. Ошибки пишутся в quarantine‑топик. |
| **ML**          | Контроль дрейфа данных            | Для ML‑моделей отслеживается статистическое расхождение между тренировочными данными и продакшен‑фичами (Data Drift, Model Drift). Алерты в Prometheus.                           |
| **DWH**         | Согласованность с боевой системой | Ежедневная сверка контрольных сумм (количество заказов, суммарная выручка) между OLTP‑базами и витринами ClickHouse.                                                              |
| **Глобально**   | Data Lineage                      | Внедряется OpenLineage / Marquez для отслеживания происхождения каждого датасета от исходного топика до BI‑отчёта.                                                                |

### 3.3 Диаграмма C4 (контейнеры) аналитического пайплайна

```plantuml
@startuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml

Person(data_scientist, "Data Scientist", "Обучает модели, исследует данные")
Person(business_analyst, "Бизнес-аналитик", "Строит отчёты, мониторит метрики")
Person(manager, "Продуктовый менеджер", "Принимает решения на основе BI")

System_Boundary(go_future_platform, "GoFuture Platform v2.0 – Аналитический пайплайн") {

    ' Доменные сервисы (существующие)
    System_Boundary(services, "Domain Services") {
        Container(trip_svc, "Trip Service", "Go")
        Container(payment_svc, "Payment Service", "Kotlin")
        Container(pricing_svc, "Pricing Service", "Rust")
        Container(fraud_svc, "Fraud Detection", "Python")
        Container(geo_svc, "Geography Service", "Go")
    }

    ' Шина событий
    ContainerQueue(kafka, "Event Bus", "Apache Kafka", "Центральная шина событий")

    ' CDC уровень
    Container(debezium, "Debezium CDC", "Kafka Connect", "Захват изменений из баз сервисов (PostgreSQL)")

    ' Data Lake и DWH
    Container(kafka_connect_s3, "Kafka Connect S3 Sink", "Kafka Connect", "Копирует топики в Data Lake в формате Parquet")
    ContainerDb(data_lake, "Data Lake", "S3/MinIO", "Сырые исторические данные (Parquet)")

    ' Compute & ML слой
    Container(flink, "Flink Cluster", "Apache Flink", "Real‑time агрегации и онлайн‑фичи для ML")
    Container(spark, "Spark Cluster", "Apache Spark", "Batch ETL: очистка, джойны, загрузка в ClickHouse")
    ContainerDb(clickhouse, "DWH", "ClickHouse", "Колоночная аналитическая БД (витрины)")

    System_Boundary(ml_platform, "ML Platform") {
        Container(jupyter, "JupyterHub / SageMaker", "Notebooks", "Эксперименты и обучение моделей")
        Container(mlflow, "MLflow Registry", "Model Registry", "Управление версиями и стадиями моделей")
        Container(model_serving, "Model Serving", "Seldon Core", "Инференс моделей (gRPC/REST)")
    }

    ' BI слой
    Container(superset, "Superset", "BI Tool", "Дашборды для бизнеса")

    ' Schema Registry (качество данных)
    Container(schema_registry, "Schema Registry", "Confluent SR", "Валидация схем событий")
}

' Потоки данных
Rel(trip_svc, kafka, "Публикация событий (Transactional Outbox)")

Rel(fraud_svc, kafka, "Публикация событий")
Rel(geo_svc, kafka, "Прямой стрим координат водителей")

Rel(debezium, kafka, "CDC стримы из БД", "Avro")

Rel(kafka, kafka_connect_s3, "Читает топики и пишет в S3")
Rel(kafka_connect_s3, data_lake, "Паркет‑файлы")
Rel(kafka, flink, "Real‑time чтение", "Avro/Protobuf")
Rel(kafka, spark, "Batch чтение топиков (при необходимости)")

Rel(spark, data_lake, "Читает сырые данные для ETL", "Parquet")
Rel(spark, clickhouse, "Записывает очищенные витрины", "JDBC")
Rel(flink, model_serving, "Отправляет фичи для инференса", "gRPC")
Rel(flink, kafka, "Публикует результаты (Surge)")

' ML поток
Rel(data_scientist, jupyter, "Работает с ноутбуками")
Rel(jupyter, data_lake, "Читает исторические данные для тренировки")
Rel(jupyter, mlflow, "Регистрирует обученную модель", "REST")
Rel(mlflow, model_serving, "Деплой модели", "REST/gRPC")

' Вызовы инференса из доменных сервисов
Rel(fraud_svc, model_serving, "Проверка на фрод", "gRPC (mTLS)")
Rel(pricing_svc, model_serving, "Динамический коэффициент", "gRPC (mTLS)")

' BI
Rel(clickhouse, superset, "SQL Queries")
Rel(business_analyst, superset, "Создаёт дашборды")
Rel(manager, superset, "Просматривает отчёты")

' Качество данных
Rel(trip_svc, schema_registry, "Регистрация/валидация схемы")
Rel(payment_svc, schema_registry, "Регистрация/валидация схемы")
Rel(debezium, schema_registry, "Использует схемы CDC")
Rel(spark, schema_registry, "Валидирует при чтении")

@enduml
```

**Пояснения к диаграмме:**  

- Доменные сервисы публикуют события в Kafka, как было заложено в ADR‑002.  
- Debezium стримит изменения напрямую из PostgreSQL‑баз тех сервисов.  
- Kafka Connect S3 Sink перекачивает сырые топики в Data Lake, где они хранятся в дешёвом и эффективном формате Parquet.  
- Flink и Spark решают комплементарные задачи: Flink – задержка <1 сек для онлайн‑фич, Spark – сложная пакетная очистка и построение витрин.  
- ML‑платформа обеспечивает полный цикл от эксперимента до продакшен‑инференса. Существующие Fraud и Pricing сервисы обращаются к Model Serving синхронно.  
- BI‑инструмент Superset подключается к ClickHouse и предоставляет готовые отчёты бизнесу.

## 4. Альтернативы

- **Только Batch (чистый Lambda) без Real‑Time Stream Processing:** недопустимо, так как динамическое ценообразование и фрод‑мониторинг требуют задержки менее секунды.
- **Чистая Kappa‑архитектура (вся аналитика через Kafka Streams, без Data Lake):** теряется возможность долговременного хранения и гибкого репроцессинга исторических данных на новых моделях; отладка стримов сложнее.
- **Закрытая BI‑платформа (Tableau, Power BI) вместо Superset:** выше стоимость лицензий, ниже гибкость встраивания в CI/CD. Superset выбран как open‑source альтернатива с хорошей интеграцией с ClickHouse.
- **Обучение моделей на сырых данных из Kafka без Data Lake:** перегружает Kafka и усложняет повторное обучение на полной истории. Data Lake необходим.

## 5. Компромиссы

- **Дублирование бизнес‑логики.** Некоторые агрегации вынужденно реализованы дважды: в стриме (Flink) для быстрого отклика и в батче (Spark) для полной точности. Это требует дисциплины и тестирования, но оправдано разделением контуров «быстро» и «точно».
- **Операционная сложность.** Для поддержки такого стека (Kafka Connect, Flink, Spark, MLflow, Seldon, ClickHouse) требуется полноценная команда Data Engineering и MLOps, а также зрелые процессы DevOps.
- **Затраты на инфраструктуру.** Data Lake значительно увеличивает объём хранилища, но за счёт формата Parquet и иерархического жизненного цикла (переход на холодное хранение) стоимость контролируема.
- **Согласованность данных между стримом и батчем.** Алерты и сверки (см. качество данных) позволяют вовремя выявлять расхождения, но не устраняют саму природу eventual consistency.
