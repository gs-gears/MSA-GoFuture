# ADR-005: Проектирование мультитенантной платформы для партнёров

**Статус:** ⚠️ На рассмотрении

**Участники:** Глушенко Сергей

**Дата:** 2026-04-26

---

## 1. Контекст

Бизнес-цель GoFuture — быстрый выход на новые рынки через партнёрскую экосистему. Партнёры (локальные таксопарки, e‑commerce, банки) должны получать изолированную, кастомизируемую среду, доступную через API самообслуживания. При этом необходимо обеспечить строгую изоляцию данных, ролевой доступ (RBAC), возможность подключения корпоративного SSO и полную наблюдаемость мультитенантного окружения.  
Архитектура платформы уже переведена на микросервисы с событийной шиной Kafka и централизованным IAM (Keycloak). Настоящее решение развивает её до мультитенантной, позволяя регистрировать нового партнёра за часы без ручного вмешательства DevOps.

## 2. Требования

- **Полная изоляция данных** партнёров на уровне базы данных.
- **Модель RBAC** с минимум четырьмя ролями (см. таблицу).
- **Единая точка входа (SSO)** с возможностью подключения корпоративных IdP партнёров (OIDC/SAML).
- **Автоматизированный onboarding** нового партнёра через API (Tenant Management Service).
- **Мониторинг и трассировка** с тегированием `tenant_id` для выявления «шумного соседа» (Noisy Neighbor).
- **Ограничение потребления ресурсов** (Rate Limiting) на уровне API Gateway согласно тарифному плану.
- **Кастомизация функциональности** для отдельных партнёров (например, локальные платёжные шлюзы, брендирование).

## 3. Решение

### 3.1 Модель изоляции данных (Bridge Model: Shared Database, Separate Schema)

Выбрана компромиссная модель **Bridge**:

- Единый кластер PostgreSQL для каждого микросервиса (или группы комплементарных сервисов).
- Под каждого партнёра создаётся **отдельная схема** (`tenant_id`).  
- На уровне приложения data source динамически задаёт `search_path` в схему нужного тенанта, извлекая `tenant_id` из JWT.  
- **Физическая изоляция на уровне схемы:** SQL-инъекция или ошибка кода одного партнёра не могут затронуть таблицы другого, так как они находятся в разных неймспейсах.

Этот подход обеспечивает лучшую безопасность, чем **Pool** (общие таблицы с tenant‑колонкой), и меньшие эксплуатационные расходы, чем **Silo** (отдельные базы на партнёра). Модель Silo может применяться для крупнейших партнёров, требующих выделенного оборудования, но для массового подключения Bridge оптимален.

### 3.2 Identity & Access Management (IAM)

- **Keycloak** используется как центральный сервер авторизации. Для каждого партнёра создаётся **отдельный Realm** или, где требуется корпоративный SSO, настраивается Identity Provider (OIDC/SAML) внутри общего Realm.
- **RBAC** включает роли, перечисленные в таблице ниже. Роли уровня `Tenant` ограничены доступом только к своему `tenant_id`, который зашивается в JWT‑токены.
- **API Gateway** (Kong) выполняет:
  - Проверку JWT и ролей.
  - Rate Limiting на основе `tenant_id` из токена, согласно лимитам договора.
  - Маршрутизацию к микросервисам.

### 3.3 Ролевая модель и уровни доступа

| Роль                   | Уровень владения     | Зона ответственности и права доступа                                                                                                                   | Изоляция данных                                                                               |
| ---------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| **Global Admin**       | Платформа (GoFuture) | Супер администратор платформы. Управление тенантами, глобальный мониторинг инфраструктуры, установка тарифных ограничений.                             | Полный доступ. Видит все схемы, но не читает партнёрские данные без явного аудита.            |
| **Platform Analyst**   | Платформа (GoFuture) | Сводная аналитика и data science. Обучение глобальных моделей.                                                                                         | Доступ к обезличенным агрегатам в Data Lake и ClickHouse (без явных user‑id и tenant‑id).     |
| **Tenant Admin**       | Тенант (Партнёр)     | Владелец таксопарка. Настройка интерфейсов, тарифов, управление пользователями своего тенанта (создание диспетчеров). Просмотр отчётности по выплатам. | Полный CRUD в рамках своего `tenant_id`. Физически не может получить данные другого партнёра. |
| **Tenant Dispatcher**  | Тенант (Партнёр)     | Диспетчер парка. Создание/отмена заказов, просмотр живой карты машин.                                                                                  | R/W доступ, строго ограниченный `tenant_id`.                                                  |
| **Passenger / Driver** | Тенант (Партнёр)     | Конечный пользователь. Создание/принятие поездок.                                                                                                      | Доступ только к своим данным (`user_id` + `tenant_id`).                                       |

### 3.4 Автоматизированный процесс подключения нового партнёра (Onboarding)

Процесс оркестрируется **Tenant Management Service** (новый микросервис) и выглядит так:

1. B2B‑менеджер GoFuture отправляет POST‑запрос в Tenant Management Service с параметрами: название, регион, тарифный план.
2. Сервис вызывает Keycloak Admin API, создавая изолированный Realm / клиентскую группу, первого Tenant Admin с временным паролем.
3. Публикуется событие `platform.tenant.created.v1` в Kafka.
4. Специализированные воркеры (Database Provisioning Workers) подписаны на это событие. Для каждого микросервиса, владеющего данными (Booking, Driver, Payment и т.д.), воркер выполняет Flyway/Liquibase миграции, создающие полный набор таблиц в новой схеме (`tenant_<id>`).
5. Когда все воркеры сообщают о готовности (через событие `platform.tenant.schema.ready.v1`), статус тенанта становится `READY`.
6. Партнёру отправляется welcome‑письмо с инструкциями и ссылкой на его административную консоль.
7. При необходимости активируются специфичные для региона sidecar‑адаптеры (например, локальный платёжный шлюз) через конфигурацию в Service Mesh.

Весь процесс полностью автоматизирован, занимает не более 10 минут и не требует участия DevOps.

### 3.5 Мониторинг мультитенантного окружения

Для предотвращения эффекта «Noisy Neighbor» и оперативного реагирования на проблемы конкретного партнёра:

- **Prometheus:** все метрики микросервисов, экспортируемые через микрометр, снабжаются меткой `tenant_id`.  
  - Графана содержит дашборды с фильтрацией по тенанту: `Error Rate`, `Latency p95`, `Throughput`.
  - Настроены алерты, если один тенант потребляет непропорционально много ресурсов, нарушая SLA других.
- **Jaeger:** каждый спан помечается тегом `tenant_id`, что позволяет трассировать медленные запросы до конкретной схемы базы данных или сервиса.
- **Kafka:** топики для критичных событий могут быть партиционированы по `tenant_id`, гарантируя изоляцию обработки.
- **API Gateway (Kong):** собирает метрики трафика по `tenant_id` и накладывает лимиты, предотвращая DDoS со стороны отдельного партнёра.

### 3.6 Диаграмма C2 мультитенантной платформы

Диаграмма отображает внедрение Tenant Management Service, взаимодействие с IAM, базы данных с несколькими схемами и процесс онбординга.

**Пояснение:**  

- Tenant Management Service выполняет только оркестрацию и не имеет собственной базы данных (state хранится в событиях или отдельном key‑value store).  
- Provisioning Workers могут быть реализованы как отдельные процессы или как дополнительные поды, автоматически запускаемые по событию (KEDA).  
- Доменные сервисы получают `tenant_id` из JWT и устанавливают `search_path` перед каждым запросом через кастомный middleware.  
- Мониторинг позволяет техподдержке быстро идентифицировать конкретного партнёра, вызывающего аномалии.

## 4. Альтернативы

- **Silo Model (Database per Tenant):** максимальная изоляция и производительность, но высокая стоимость инфраструктуры и сложность управления для тысяч маленьких партнёров. Может быть применена для крупнейших партнёров, но не как общая стратегия.
- **Pool Model (Tenant Column):** самая простая, но слабая изоляция. Риск утечки данных при ошибке в коде, сложнее обеспечить compliance. Отвергнута из‑за требования «полной изоляции».
- **Единый Realm в Keycloak с группами:** не позволяет обеспечить полноценную изоляцию учётных записей партнёров и их кастомные IdP. Использование отдельных Realm для каждого партнёра даёт лучшую управляемость.
- **Ручной онбординг через тикеты:** недопустим при масштабировании на сотни партнёров, противоречит цели time‑to‑market 2–4 недели.

## 5. Компромиссы

- **Совместное использование базы данных (общий кластер) означает риск конкуренции за ресурсы (CPU, I/O).** Необходимо тщательное планирование ёмкости и мониторинг. Для особо нагруженных партнёров может применяться выделенный пул соединений или отдельный read‑replica.
- **Сложность миграции схемы при добавлении новых фич:** каждое изменение должно быть применено ко всем схемам. Это автоматизируется через те же механизмы provisioning (воркер для миграций), но увеличивает время отката.
- **Динамическая установка `search_path` может усложнить использование ORM и кеширование соединений.** Требуется аккуратная работа с пулами соединений (например, добавление перехватчика в HikariCP).
- **Keycloak Admin API для создания Realms требует повышенных привилегий и мониторинга безопасности.** Необходимо ограничить Tenant Management Service минимально необходимыми правами.
